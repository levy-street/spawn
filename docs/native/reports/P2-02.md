# P2-02 — Onboarding and host pairing

## What I built

Implemented the complete phone-side onboarding and manual host-pairing ceremony:

- Derived Account → Verify → Host → Done resolution from live account/host state, including the
  exact per-device host-skip key.
- Native `/onboarding` and authenticated `/device` pairing surfaces.
- Mac/Linux install instructions with the deployment-aware installer command, exact fallback
  command, clipboard feedback, `spawnd login` instruction, and no phone-hosting or QR claim.
- Eight-character one-time-code entry using the shared `Input` and validator, automatic uppercase
  formatting as `QZ4K-7HMT`, and compact wire normalization.
- Pending-host lookup with local Ed25519 fingerprint derivation and strict equality against the
  server claim before anything is reviewable.
- A prominent mutual fingerprint ceremony: deliberate host-fingerprint confirmation before
  approval, then deliberate phone-fingerprint confirmation against the daemon output.
- Pin-first approval through P1-06's pin store and bounded `deviceIdentity.signApproval`, followed
  by exact response-tuple revalidation. Signature buffers are zeroed after use.
- Explicit revoked-pin reapproval, retained-pin retry after incomplete server approval, and
  fail-closed screens for mismatch, missing/revoked identity, unreadable identity/pin storage,
  revoked pins, expiry, unknown code, pending host proof, invalid endorsement, and rejection.
- Endorsement discovery/acceptance for another registered device, with local signature
  verification, explicit endorser-fingerprint comparison, and the Expo Go passkey-PRF unavailable
  state from P1-06.
- Shared success/error haptics only through P1-04's vocabulary.

The `impeccable` guidance was limited by the assignment's ban on creating root `.impeccable.md`;
the supplied native research and frozen tokens provided the design context instead. It influenced
the deliberate information hierarchy and security confirmations without changing the reference
design language.

## Deviations from plan and research

1. The plan cites `research/12 §4` as onboarding; the current report's actual onboarding and
   pairing sections are §§9–10. Those sections were used. No `web/` source consultation was needed.
2. `DevicePendingResponse` contains no ceremony creation or expiry timestamp. The UI therefore
   starts a maximum 30-minute review countdown when the phone successfully looks up the code and
   still maps the server's authoritative earlier expiry to the expired state. Exact remaining time
   from daemon creation cannot be calculated from the frozen API contract.
3. P1-05 exposes endorsement listing/creation but no acknowledgement/deletion endpoint. Verified
   endorsements are accepted into the local pin store, but the client cannot acknowledge the
   consumed introduction through an API that does not exist.
4. Added the research-required `/device` route so pairing and endorsement remain accessible for an
   already-onboarded account; this is within the owned onboarding route directory.

## Known gaps

- The displayed countdown is a safe local review-window timer, not exact time remaining since the
  daemon created the code; the server remains authoritative and rejects earlier expiry.
- Another registered account device is only presented as a possible endorsement route. It is not
  treated as host-trusted until a server introduction arrives and verifies locally.
- No simulator, Expo Go, screenshot, or physical-device test was performed, per campaign rules.
- Repository-wide lint remains blocked by the single P2-04-owned import-order finding above.
