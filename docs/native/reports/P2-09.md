# P2-09 — Alerts, notifications and attention badges

## What I built

- A root-mountable `AlertPresenter` that consumes P1-08's transient in-memory alert store, maps
  alerts to exact web-parity titles/details, shows tappable in-app toasts, routes to
  `/terminal/{sessionId}`, applies semantic haptics, and removes handled alert records so the store
  never becomes an inbox.
- Delivery suppression for disabled event classes, muted sessions, duplicate/in-flight events,
  and the terminal currently visible to the user. Alert dedup remains the P1-08 store's bounded
  30-second delivery guard, not a server acknowledgement.
- Exact device-local notification preferences at `spawn.notify.prefs`, including safe
  normalization, a newest-200 muted-session bound, external-store subscriptions, session mute
  helpers, and account-clear behavior.
- Explicit-permission local notification delivery through `expo-notifications`. Permission is
  requested only when the user explicitly enables system notifications. Notifications are
  immediate, carry route identifiers rather than terminal content, never set an OS badge, and are
  rate-limited per session for 30 seconds.
- Notification tap handling that refreshes the singular session query before opening the native
  terminal route, with a safe stale-session fallback.
- An explicit capability model: local notifications are available; remote push and delivery while
  suspended/closed are unavailable, with a user-facing reason that states both the Expo Go and
  missing-server-path constraints.
- `AttentionSummary` wiring over P1-07's `sessionAttention`, `attentionRank`, `tabStats`, and
  `workspaceStats`, plus an accessible reusable `AttentionBadge` with count and dot displays.
  Dead-session attention takes visual precedence over awaiting-input attention while retaining
  both counts.
- Five focused test suites covering formatter copy, delivery mapping, real presenter routing and
  dedup, current-session suppression, selector precedence, badge accessibility, preference
  normalization, explicit permission timing, rate limiting with fake timers, permission denial,
  safe notification data, and remote capability reporting.

## Adoption APIs

### App shell transient presentation

Mount `AlertPresenter` once inside the Expo Router, TanStack Query, toast, and realtime providers:

```tsx
import { AlertPresenter } from "@/components/alerts/alert-presenter";

<AlertPresenter />
```

It derives the current terminal from the route. Tests or alternate shells may pass
`currentSessionId` and/or `onOpenSession` explicitly.

### Workspace, tab, and terminal attention badges

```tsx
import { AttentionBadge } from "@/components/alerts/attention-badge";
import {
  sessionAttentionSummary,
  tabAttentionSummary,
  workspaceAttentionSummary,
} from "@/data/queries/alerts";

<AttentionBadge summary={workspaceAttentionSummary(workspace, sessionsById)} />
<AttentionBadge summary={tabAttentionSummary(tab, sessionsById)} />
<AttentionBadge display="dot" summary={sessionAttentionSummary(session)} />
```

`summary === null` renders nothing. Count mode caps only its displayed text at `99+`; the
accessible label retains exact dead/waiting counts.

### Settings integration

`useNotificationPreferences()` from `@/data/queries/alerts` returns:

```ts
{
  prefs,
  setPreference(key, value),
  setSystemEnabled(enabled),
  setSessionMuted(sessionId, muted),
}
```

`setSystemEnabled(true)` is the only API that requests notification permission. Capability and
reason copy are exported as `notificationCapabilities` from `@/lib/notifications`.

## Deviations and research notes

1. The P2-09 plan cites research/10 sections 4 and 9 for alert preferences and Expo
   notifications, but the current report places that material in sections 8 and 11. I used the
   actual section contents.
2. Research/10 describes behavior but not the literal alert formatter strings. I consulted only
   `web/src/lib/alerts.ts` for the missing title/body copy and deduplication rules; the research was
   silent rather than incorrect.
3. The plan requires rate limiting but does not specify a duration. The implementation uses a
   per-session 30-second window, matching the existing alert-store dedup/claim TTL. The timestamp
   is recorded only after successful native scheduling, so a native scheduling failure does not
   block a retry.
4. The fixed dependency set does not include `expo-audio`, so there is no separate foreground
   two-note cue. Background local notifications honor the existing `sound` preference through
   their native notification content, and all requested toast/haptic/system behavior is present.

## Known gaps

- The server has no APNs, FCM, Expo Push Service, or Web Push subscription/delivery path. Expo Go
  cannot receive remote push. A suspended or terminated app therefore cannot learn about a newly
  generated alert; this is reported explicitly by the capability model and is not disguised as a
  queued notification.
- An immediate local notification can be scheduled only if the alert socket frame reaches JS
  during the app's executable background window.
- No physical-device, simulator, Expo Go, or manual notification-permission test was performed,
  per campaign rules.
- Final end-to-end alert delivery depends on the requested P3-01 app-shell mount and the P2-08
  preference-store consolidation.
