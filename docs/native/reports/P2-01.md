# P2-01 — Auth screens, session bootstrap, and auth gate

## What I built

- Five native auth screens plus the auth stack layout: login, signup/invite, forgot password,
  reset password, and verify email.
- A shared keyboard-aware auth shell using the campaign typography, spacing, colour, radius,
  shadow, and motion tokens, with native safe-area and interactive keyboard dismissal behavior.
- Login and signup mutations that use P1-05's endpoint contract, which captures the 30-day
  `spawn_session` cookie before resolving. The short JSON `access_token` is never persisted.
- React Query bootstrap hooks for auth config, `me`, and hosts. Successful login/signup clears
  prior-account query snapshots before seeding `qk.me()`.
- A live-state `AuthGate`: SecureStore token → auth config/account → hosts. It subscribes once to
  `subscribeUnauthenticated`, clears query snapshots, and replaces the stack with Login once per
  authenticated generation.
- Signed-in verification waiting/resend with five-second account polling, public verification-link
  confirmation deduplicated once per token per app process, and signed-out success handling.
- Disabled configured OAuth providers with the visible reason “Available in installed builds”.
- Deep-link token/invite consumption without logging or persisting sensitive query values.
- Exact authored recovery/link/server copy from research/12, including distinct expired versus
  used/superseded link messages and enumeration-resistant forgot-password behavior.

The `impeccable` guidance influenced the restrained press-sheet hierarchy, registration marks,
poster/sigil typography, spacing rhythm, and accessibility pass while the campaign tokens and
reference remained authoritative.

## Deviations from the plan

1. The plan says the login success path calls `authToken.captureFromResponse(res)`. P1-05's frozen
   endpoint implementation deliberately hides the raw `Response` and performs this capture through
   `ApiRequestInit.onResponse` inside `logIn`, `signUp`, and `confirmPasswordReset`. P2-01 uses those
   endpoints rather than duplicating them; its integration test spies on `captureFromResponse` and
   proves it runs before `me` is seeded and that the short token is not stored.
2. Research/01's web AuthShell uses a fixed grimoire/pressroom palette and altar artwork. The
   shared native primitives consume only the current `ThemeProvider` and no scoped theme override
   exists; P2-01 also cannot write final assets. The native shell therefore reproduces the
   composition and tokenized typography/marks/plate using the active semantic theme, with a
   token-built fallback lockup. This avoids bypassing shared `Field`/`Input`/`Button` primitives.
3. There is no semantic five-second auth-poll token. Verification polling reuses the shared
   5,000 ms duration token so the exact interval is not hard-coded in the component.
4. The auth-shell layout detail was absent from research/01 beyond its palette, typography, and
   artwork notes, so I consulted only `web/src/components/onboarding/auth-shell.tsx` for its actual
   stacked composition. The research copy remained authoritative for all flows.
