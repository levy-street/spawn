# P1-06 — Device identity, crypto and trust

## What I built

- Expo-Go-safe cryptographic bootstrap: Expo Crypto supplies `getRandomValues`; Noble's sync and async SHA-512 hooks are installed idempotently and checked at every crypto entry point.
- Strict byte codecs for canonical base64, base64url, hex, UTF-8, and UUIDs without `Buffer`, `atob`, `btoa`, or added polyfills.
- Pure Ed25519 signing and RFC 8032 verification (`zip215: false`) with canonical/off-curve/small-order public-key rejection and mixed-torsion interoperability controls.
- One account-scoped device identity per SecureStore record. First use is serialized, seed/public-key consistency is self-tested, seeds are never cached or exported, and signing is limited to protocol transcripts.
- Revision-2 signed RTC signal transcript and exact 12-field wire-envelope parsing, topology checks, serialization, signing, and verification.
- Registration, host-pair approval, host possession, and browser endorsement transcript encoders plus their protocol-specific sign/verify helpers.
- Durable SQLite host pins keyed by `(account ID, exact server origin, full host public key)`, with bounded aliases/tombstones and explicit fail-closed resolution states.
- Browser-device registration/revocation and endorsement verification/acceptance/creation flows using P1-05's endpoint and schema types.
- A minimal SecureStore wrapper with a deterministic 2,048-byte UTF-8 value bound, plus an explicit Expo Go passkey-PRF unavailable capability.

## Exact transcript layouts

All integer lengths/versions are unsigned big-endian; all public keys are strict 32-byte Ed25519 encodings; all signatures are pure Ed25519 over these exact bytes.

- Browser registration v1, 74 bytes: `"SPAWN-BROWSER-REGISTER-V1"[25] | 0x01 | account UUID[16] | browser key[32]`.
- Host approval v1, 139 bytes: `"SPAWN-HOST-PAIR-APPROVE-V1"[26] | 0x01 | account UUID[16] | approval nonce[32] | host key[32] | browser key[32]`.
- Host possession v1, 126 bytes: `"SPAWN-HOST-PAIR-POSSESSION-V1"[29] | 0x01 | device code[32] | approval nonce[32] | host key[32]`.
- Browser endorsement v1, 153 bytes: `"SPAWN-BROWSER-ENDORSE-V1"[24] | 0x01 | account UUID[16] | host key[32] | endorser key[32] | endorsed key[32] | endorsed-device UUID[16]`.
- Signed signal revision 2, `143 + SDP byte length`: `"SPAWN-RTC-SIGNAL-SIG-V1"[23] | 0x02 | kind[1: offer=1, answer=2] | protocol version[u32] | session text length[u16] | canonical UUID text[36] | scope[1: session=1, host=2] | scope text length[u16] | canonical UUID text[36] | role[1: browser=1, daemon=2] | intended-peer key[32] | SDP length[u32] | strict UTF-8 SDP`.

The wire parser requires exactly 12 fields, canonical UUID text, strict keys/signature, and fixed topology: `spawn.pty` is version 2/session; `spawn.host.ctl` is version 1/host; offers are browser-sent and answers daemon-sent. Protocol strings and sender key are authenticated by exact envelope validation and signature-key selection, not inserted as transcript fields. There is no timestamp.

Fingerprint display format is `SHA256:` plus unpadded base64url of the first 12 SHA-256 bytes of the full public key.

## Deviations from the plan/research

- Research mentions `base64-js`/`@stablelib/utf8` as possible installed helpers, but neither is a direct scaffold dependency. Per the plan's explicit local-helper allowance and dependency freeze, I implemented strict byte codecs locally instead of adding packages.
- The frozen `deviceIdentity` contract has no account argument although identity is account-scoped. I added explicit `setDeviceIdentityAccount`/`clearDeviceIdentityAccount` selectors while preserving the frozen object methods exactly. Before a server registration exists, `ensure().deviceId` is a stable UUID derived from the public-key hash; the registration endpoint's returned UUID remains authoritative server identity.
- The owned Jest config exists solely to demonstrate the required Noble ESM transform. I did not edit the unowned root `package.json`.
- The fixture filenames retain `v1`, but their signal transcript bytes begin with revision `0x02` and use `session`; implementation follows the research warning and golden bytes. No research-versus-fixture byte discrepancy was found.
