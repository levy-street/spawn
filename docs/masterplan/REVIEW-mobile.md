# REVIEW-mobile — connection layer of the Expo client

Branch `native-daemon-fixes-auto-update-daemon`, read-only, code-reading only (no builds/tests run). Paths are relative to `mobile/` unless prefixed. Line numbers are from the working tree at review time; other agents were editing concurrently, so treat them as approximate anchors.

Architecture as read: three `ReconnectingSocket`s (`/ws/alerts` with an 80 s watchdog; `/ws/browser` and `/ws/host` with no watchdog) live in RN. The RTCPeerConnection lives inside a WKWebView (`worker-transport.js`), driven over a JSON `postMessage` bridge by `session-transport.ts` / `host-transport.ts`. RN signs offers and verifies answers; the worker never sees the private key. Lifecycle: `lifecycle.ts` retires every socket on `background` and runs a resume sweep on `active`; the two surfaces additionally close/reopen their transport on their own `AppState` listener.

## (A) Findings

### P1-1 — Host control transport never reconnects after a drop; every later request fails "not_ready"
**Evidence.** `src/terminal/transport/host-transport.ts:662-664` handles a worker `state` message by `this.#setState(message.state)` and nothing else. The worker posts `state: "reconnecting"` on any channel/peer failure (`src/terminal/worker/worker-transport.js:44-50`) after tearing the peer down. The session transport has `#scheduleReconnect` (`session-transport.ts:344-345, 459-472`); the host transport has no equivalent — grep for `reconnect` in `host-transport.ts` finds nothing. `request()` rejects while not ready (`host-transport.ts:226-230`). The connect watchdog was cleared at ready (`:798`), so nothing ever times out into `failed` either.
**Field impact.** Any blip on the host channel (Wi-Fi ↔ cellular, a 5 s ICE disconnect, daemon restart) leaves the file explorer on "Connecting to host files" forever (`src/components/files/file-explorer.tsx:233-236` — `!ready` spinner) and the launcher/session-target sheets with a dead transport. `file-explorer.tsx:198-208` only handles `failed`, with no Retry. Users must leave the screen and come back.
**Fix.** Mirror the session transport: on `state === "reconnecting"` call a new `#scheduleReconnect()` that re-arms `#armConnectWatchdog()`, re-runs `#startSignal()` (a fresh `/ws/host` socket yields a fresh `rtc.config`, including fresh TURN creds), and rejects in-flight `#pending`/`#commands` with a retryable `connection_lost` error so callers can retry. Give `file-explorer.tsx` a Retry on `failed` (remount `HostTransportSurface` with a generation key, as `terminal-overlay.tsx:275-288` already does for sessions).

### P1-2 — A repeat `rtc.config` mid-session tears down a healthy WebRTC session and desyncs the RN state machine (input silently dropped)
**Evidence.** The server sends `rtc.config` on every `/ws/browser` connection (`server/spawn_server/ws/browser.py:217`). The session signalling socket reconnects on its own (`session-signal.ts:61-68`, linear 500 ms steps) — after a server deploy, an idle proxy close, or the socket-observed "interface change" sweep (`provider.tsx:123-127` retires it, `:131-134` reopens it). `session-transport.ts:286-309` reacts to *every* `rtc.config` by sending `connect` with a new `rtcSessionId`; the worker's guard `if (state.pc && state.rtcSessionId === message.rtcSessionId) return` (`worker-transport.js:69`) therefore never matches, and `teardown(false)` (`:70`) closes the live peer and both channels (with no `rtc.close` to the daemon).
Meanwhile the RN machine never left phase `ready`: `reduceConnection` only accepts `signal-open` from `signalling`/`reconnecting` (`state-machine.ts:70-72`) and `gate` only in `connecting` (`:73-77`). The worker posts a plain `state: "connecting"` (RN sets state `connecting`, `session-transport.ts:346-347`), then the first gate arrives; `session-transport.ts:339-341` reduces it (no-op) and sets state to `this.#machine.phase` = `ready` on the **first** gate (`bindingAccepted`), before `ptyOpen`. `#setState("ready")` flushes buffered input (`:437-440`); the worker's `sendPty` returns `false` when the channel is not open (`worker-runtime.js:673-675`) — the keystrokes are lost with no error.
The web guards this: `startRtc` is a no-op while `rtcRef.current.pc` exists (`web/src/components/terminal/useSessionSocket.ts:419`).
**Field impact.** Every signalling-socket reconnect during a live terminal costs a full renegotiation (5–15 s on cellular) plus a duplicated history replay (P1-6), and any input typed in the window is dropped. On the socket-observed network epoch this is the only thing that "recovers" the RTC, which hides that P1-4 has no real trigger.
**Fix.** In `session-transport.ts#handleSignalFrame` (and `host-transport.ts:609`) act on `rtc.config` only when `this.#machine.phase === "signalling"` (i.e. we asked for it) — otherwise just cache `ice_servers`/policy for the next retry. Additionally make `reduceConnection` robust: a `signal-open` from `ready` should reset gates and go to `connecting`, and the worker should ignore a `connect` while `pc.connectionState === "connected"`.

### P1-3 — Session reconnect backoff never resets and starts at 5 s; one failed reconnect is terminal
**Evidence.** `state-machine.ts:58-60` `reconnectDelay = min(60 s, 5 s·2^attempt)`. `disconnect` increments `reconnectAttempt` (`:79-88`); nothing resets it except `open` from `idle`/`closed` (`:67-69`) — reaching `ready` does not. So the 1st drop waits 5 s, the 2nd 10 s, then 20/40/60 s for the rest of the surface's life, on top of the worker's own 5 s "disconnected" grace (`worker-transport.js:108-110`). If the retry's 25 s watchdog (`session-transport.ts:474-481`) fires, `#fail("connect_timeout")` → `failed` (`:505-517`), the state machine's `retired` flag is set, and there is no automatic further attempt: the user must tap Retry. The web resets `rtcRetryAttempts` on every `rtc.config` (`useSessionSocket.ts:1316`) and keeps retrying with a capped backoff (`:404-416`).
**Field impact.** Poor-signal phone: the 3rd blip of the day means 25 s of "Reconnecting" before signalling even starts; a tunnel that outlasts one 25 s attempt leaves the terminal on "Connection failed — The host did not answer in time. It may be offline, or it may not have approved this device." (`CONNECT_TIMEOUT_MESSAGE`, `:51-52`), which is the wrong diagnosis.
**Fix.** In `reduceConnection`, reset `reconnectAttempt` to 0 when a `gate` completes readiness (or on `signal-open`). Use a faster ladder for the first attempts (e.g. 500 ms, 1 s, 2 s, 4 s … cap 30 s, jittered like `socket.ts:255-260`). On `connect_timeout` during a *reconnect* (not the initial open) keep retrying under the backoff instead of `#fail`, up to a budget (web-style), and only then surface `failed` with a message that says "lost the connection" rather than "may not have approved this device".

### P1-4 — No real network-change signal: interface changes are inferred from an 80 s alert-socket watchdog
**Evidence.** `network-source.ts:10-14` documents the choice: no reachability package; `reportSocketFailure` (`:35-45`) is only called when the alerts socket goes `open → reconnecting` (`provider.tsx:106-108`). That transition needs either an OS `onclose` or the watchdog at `SOCKET_TIMING.watchdogMs = 80_000` (`socket.ts:5`, 3.2 missed 25 s pings; `server/spawn_server/ws/alerts.py:42`). `/ws/browser` and `/ws/host` have `watchdogMs: null` (`session-signal.ts:64`, `host-signal.ts:40`) and the server never pings them (no keepalive in `browser.py`/`host.py`), so they cannot detect a half-open socket at all. Nothing tells the worker to `restartIce()` — the string does not occur in `mobile/`. The only ICE reaction is the 5 s `disconnected` grace (`worker-transport.js:106-114`).
**Field impact.** Wi-Fi → cellular handoff: WebKit takes ~5–30 s to reach `disconnected`/`failed` (consent freshness), +5 s grace, +P1-3 delay, then a full re-signal. Cellular → Wi-Fi (the common "walk into the office" case): iOS keeps the cellular path up, so nothing fails; the phone stays on cellular until that path drops, and the alerts socket may stay half-open for up to 80 s.
**Fix.** Add `expo-network` (in the Expo 54 SDK; `Network.addNetworkStateListener` → `{type, isConnected, isInternetReachable}`) as the production `NetworkSource` (it already has the interface: `lifecycle.ts:10-12`), keeping the socket-observed source as a fallback. This is a native-module change → new build per `docs/RELEASE.md`. On `interface-change`, also post a new bridge message `network-changed` to the worker: call `pc.restartIce()` if the daemon supports re-offer on the same binding (open question for the daemon review), otherwise `channelFailed()` immediately without the 5 s grace. Give `/ws/browser`/`/ws/host` a server ping (or client-side `watchdogMs` of ~60 s) so a dead signalling socket is retired before it is needed.

### P1-5 — The surfaces tear the transport down on `inactive`, not just `background`
**Evidence.** `src/terminal/TerminalSurface.tsx:215-229` and `HostTransportSurface.tsx:85-96`: `if (nextState !== "active") { …transport.close() }`. iOS reports `inactive` for Control Center / Notification Center pulls, an incoming call banner, Face ID prompts, the app switcher, and any system sheet the app itself presents — the document picker used for uploads and the share sheet used by `lib/share.ts`. `lifecycle.ts:111-114` deliberately retires only on `background`; the surfaces are inconsistent with it.
**Field impact.** Peeking at Control Center, or picking a file to upload, closes the peer (`worker-transport.js:276-280`) and forces a full re-signal + history replay on return — several seconds of "Reconnecting" and (P1-6) duplicated scrollback, for no benefit. On `background` the OS will suspend the WKWebView anyway, so the close there is right.
**Fix.** Close only on `background`; on `inactive` do nothing (or start a 3–5 s deferred close that `active` cancels). Keep `retiredForBackground` semantics as they are.

### P1-6 — History replay is written on top of the existing buffer: scrollback duplicates on every reconnect/foreground
**Evidence.** The WebView and its xterm instance survive `close()`: `init` re-uses `state.term` (`worker-runtime.js:639`), and `close` only tears down the peer (`worker-transport.js:276-280`). On the next `connect`, `resetGates` zeroes `ptyOffset` (`worker-session.js:43-66`), `startBootstrap` requests 400 lines of `history` (`:133-139`), and `finishReplay` only resets the terminal for the `snapshot` operation (`:278`). The web explicitly clears with `\x1b[H\x1b[2J\x1b[3J` before a reseed because of exactly this duplication (`web/src/components/terminal/Terminal.tsx:676-687`).
**Field impact.** After every background→foreground (P1-5 makes this frequent) and every P1-3 reconnect, the last 400 lines appear twice; a TUI on the alternate screen is repainted from a flattened history (the web refuses to reseed the alternate screen, `Terminal.tsx:641-644`).
**Fix.** In `finishReplay`, when this is not the first bootstrap of this xterm instance (track a `bootstrapCount`), write `\x1b[0m\x1b[H\x1b[2J\x1b[3J` before the replay (not `term.reset()`, which drops modes), and skip the reseed when `term.buffer.active === term.buffer.alternate` unless forced.

### P1-7 — Alerts/trust socket connects once at mount; after a fresh sign-in it stays `failed` until the app is backgrounded
**Evidence.** `provider.tsx:72,139` creates the client and calls `connect()` in the mount effect (deps `:151` are all stable). `RealtimeProvider` sits above the auth gate (`src/lib/providers.tsx:87`). With no token, `socketUrl` throws `ApiError(401)` (`src/data/api/socket-urls.ts:6-7`) → `startConnection` sets `failed` (`socket.ts:159-167`). Nothing calls `connect()` again except the resume sweep (`provider.tsx:129`, only on `active`-after-`background` or a network epoch, which cannot happen with no open socket). `useRealtime()` — the only exposure of `reconnect()` — has no consumers (grep). `auth-gate.tsx:144,342` subscribes to `authToken` but only for its own state. The same holds for a permanent close (`PERMANENT_CLOSE_CODES`, `socket.ts:15`): `1008` covers "bad token"/"not authenticated" (`server/spawn_server/ws/browser.py:157-176`) and `4003` protocol-required; the store gets `alertSocket: "failed"` and no UI reads it beyond `queries/alerts.ts:167` (`=== "open"` for live/poll selection).
**Field impact.** Fresh install → sign in → no live alerts, no in-app trust knock, until the user backgrounds the app once. Degraded rather than dead: alerts fall back to polling and the knock also arrives as a push (recent commits), but the designed live path is silently off. A token that expires mid-run also lands in `failed` with no user-visible state.
**Fix.** In `RealtimeProvider`, subscribe to `authToken.subscribe` and call `alertClient.connect()` when a token appears (and `retire()` when it disappears). Treat `1008` as *retry after re-auth*, not permanent, and surface `4003` ("update SPAWN D") and persistent `failed` in the UI (a small "Live updates paused — Retry" affordance wired to `useRealtime().reconnect`).

### P2-1 — `open()` can complete after `close()`, leaving two bridge subscriptions (duplicate offers/candidates)
**Evidence.** `session-transport.ts:126` awaits `browserIdentityWire()` (secure-store read + key load) before subscribing to the bridge (`:127`) and sending `init`. `close()` (`:156-176`) settles `#opening` but cannot cancel the await; when it resolves, `open()` continues: subscribes again, sends `init`, reduces `open` from `closed` (allowed, `state-machine.ts:68`), starts signalling. The next `openTransport()` (surface AppState flip) finds `#opening === null` and runs the whole thing a second time; `#bridgeUnsubscribe` is overwritten (`:127`), so the first listener leaks and every worker message is handled twice — including `signal-frame`, so each offer/candidate is sent to the server twice. Same shape in `host-transport.ts:177-178`.
**Field impact.** A quick `inactive→active→inactive→active` (P1-5 makes these common) can double-post the offer; the daemon/server may answer with `collision` (`worker-transport.js:200-203` treats it as a failure).
**Fix.** Capture `const opening = this.#opening` before the await and bail if `this.#opening !== opening || this.#state === "closed"` afterwards; call `this.#bridgeUnsubscribe?.()` before subscribing; make `open()` a proper cancel point.

### P2-2 — Two HTTP GETs sit on the offer's critical path
**Evidence.** On `sign-request`, RN awaits `Promise.all([signWorkerRequest, loadCarriedEndorsements()])` (`session-transport.ts:353-361`, `host-transport.ts:668-676`). `loadCarriedEndorsements` calls `listBrowserDevices()` and `listAccountEndorsements()` (`src/data/trust/carried-endorsements.ts:54-55`) — network round trips — while the worker holds a created offer and buffers candidates. The trust preflight (`device-trust.ts:92-96`, three more GETs) runs in parallel and competes for the same radio.
**Field impact.** On cellular this adds one HTTP RTT (often 300 ms–2 s with cold TLS) to every connect and every reconnect, plus the endorsements are only useful when `host.supports_account_chains`.
**Fix.** Start `loadCarriedEndorsements()` (memoised, 30 s TTL like `device-trust.ts`) at `open()` time in parallel with WebView boot and signalling, and await the cached promise at sign time; skip it entirely when the host is directly pinned (`probeDeviceHostTrust` already knows). Consider also opening the signalling socket before `onLoad` (see P2-6).

### P2-3 — Signalling-socket failures are invisible to the transport; a `1008`/`4003`/`1009` close is misreported as "host did not answer"
**Evidence.** Neither transport subscribes to `signal.state`; `SignalChannelLike` exposes it (`types.ts:107-112`) but `#startSignal` only wires `onFrame` (`session-transport.ts:269-274`). A `/ws/browser` close with `1008 "session not found"` or the `protocol.required` + `4003` path (`browser.py:189-194`) puts the socket in `failed`; the transport sits until the 25 s watchdog and then shows the "may not have approved this device" copy.
**Fix.** Subscribe to `signal` state in `#startSignal`; on `failed` call `#fail("signal_failed", <close reason>)` immediately, mapping `4003` to an "update the app" message. Expose the close code/reason from `ReconnectingSocket` (store `event.code`/`event.reason` in `socket.ts:212-227`).

### P2-4 — Security hardening: JWT in the WebSocket URL, permissive CSP `connect-src`, unvalidated ICE server URLs
**Evidence.** `socket-urls.ts:10-11` puts `token=<jwt>` in the query string of all three sockets. The server accepts `Authorization: Bearer` first (`browser.py:146-150`), and React Native's `WebSocket` supports a headers option (`new WebSocket(url, protocols, { headers })`). Query tokens land in access logs, proxies, and crash reports. The worker CSP is `connect-src 'self' https: wss: ws:` (`src/terminal/worker/build-worker.mjs:42`); the worker never uses fetch/WebSocket (all signalling is bridged), so this is pure exfiltration surface for a compromised page (xterm parses hostile bytes). `ice_servers` is passed to `RTCPeerConnection` unvalidated (`worker-transport.js:80-83`; RN only checks `Array.isArray`, `session-transport.ts:290`). `originWhitelist={["*"]}` is mitigated by `onShouldStartLoadWithRequest` + `navigation-policy.ts` (test-pinned).
**Risk.** All medium-low: DTLS is end-to-end and the SDP fingerprint is inside the signed envelope, so a hostile TURN/ICE server sees ciphertext only; the JWT leak is the most concrete.
**Fix.** Send the token as a Bearer header from `ReconnectingSocket.createWebSocket` (keep the query form only for the file-URL worker fallback, which does not exist today). Tighten CSP to `connect-src 'none'` (WebRTC is not governed by `connect-src`; add `webrtc 'allow'` is unnecessary on WebKit). Filter `ice_servers` to entries whose every `urls` value matches `^(stun|stuns|turn|turns):` before the bridge send, and drop `username`/`credential` from non-TURN entries. Add a test that pins the CSP string in `TERMINAL_WORKER_HTML` next to `webview-containment.test.tsx`.

### P2-5 — No path/RTT visibility on the phone; "reconnecting" and "failed" copy is generic
**Evidence.** The web polls `pc.getStats()` every 5 s and shows direct/stun/relay + RTT (`useSessionSocket.ts:1552-1605`, `ConnectionChip.tsx`). The phone's diagnostics sheet lists only capability booleans (`diagnostics-sheet.tsx:64-85`); nothing reports whether the session is relayed or the RTT. `connectionCopy("reconnecting")` says "Restoring the connection and replaying recent output." regardless of cause (`connection-status.tsx:49-55`); `failed` shows `error.message` (`:147`) with Retry (`:157-161`) — that part is fine. The worker sends `channel_closed` with the daemon's reason (`worker-transport.js:47`) as `retryable: true`, and `terminal-overlay.tsx:463-466` stores it, so a daemon-authored reason does reach the banner — good.
**Fix.** Add a worker `getStats` poll (5 s, only while `pc.connectionState === "connected"`) posting a `connection-info { kind, rttMs, protocol }` bridge message; show it in `TerminalHeader`/diagnostics like the web chip. Vary the reconnecting copy by trigger (network change vs host closed).

### P2-6 — Serial boot: signalling starts only after WebView load + identity load
**Evidence.** `TerminalSurface.tsx:356-360` opens the transport in `onLoad` (parsing a ~700 KB inline bundle and creating xterm). Only then `open()` awaits `browserIdentityWire()` (`session-transport.ts:126`), sends `init`, and opens the `/ws/browser` socket (`:146`), whose first frame is `rtc.config`. `probeLoopback` (`worker-runtime.js:704-744`) also runs two extra `RTCPeerConnection`s at every boot, including on every hidden host worker.
**Field impact.** Roughly WebView-boot + secure-store + TLS handshake + WS upgrade before the offer can even be created; on cellular that is easily 1–2 s of the "open session → first byte" budget that could overlap.
**Fix.** Start `browserIdentityWire()` and the signalling socket from the surface's mount effect (before `onLoad`), buffer `rtc.config` in RN, and send `init`+`connect` together once `ready` arrives from the worker. Cache the loopback probe result per process (it cannot change between WebViews) and skip it for host workers.

### P2-7 — One hidden WKWebView + signalling socket + RTC session per host card on the Legion screen
**Evidence.** `legion-host-card.tsx:133-141` mounts `LiveCapacityProbe`, which mounts `HostTransportSurface` (`live-capacity-probe.tsx:73-80`) when `live && focused` (`legion-screen.tsx:130`). Each probe polls `host.metrics` every second (`:7,53`).
**Field impact.** N hosts → N WKWebViews, N `/ws/host` sockets, N DTLS sessions, N loopback probes, all reconnecting on every AppState flip (P1-5) — measurable battery and memory on a phone, and N-way contention with the terminal's own connect.
**Fix.** Share one `HostTransport` per host across consumers (a registry keyed by `hostId` with refcounts), poll at 2–5 s, and pause polling when the card is off-screen.

### P3-1 — `waitForWritable` busy-polls `bufferedAmount` every 10 ms (`worker-host.js:44-51`); use `bufferedamountlow` with `bufferedAmountLowThreshold` as `worker-session.js:570-587` already does.
### P3-2 — Worker dedupes identical bridge messages within 1 ms (`worker-runtime.js:660-671`) to cope with the double `window`/`document` listener; two legitimately identical messages (e.g. `fit`) collapse. Register only the listener the platform actually fires (`document` on Android, `window` on iOS) instead.
### P3-3 — `channelFailed` calls `teardown(false)` (`worker-transport.js:49`), so the daemon never gets `rtc.close` on a client-side failure; when the signalling socket is still open, send `rtc.close` so the daemon frees the binding sooner (helps P1-2's `collision`).
### P3-4 — `HostTransportSurface`/`TerminalSurface` both hard-code `USE_FILE_WORKER_FALLBACK = false` with a comment about a third HTTPS-origin fallback; if inline HTML ever fails the secure-context check the app has no runtime fallback, only the `worker_capability` failure (`session-transport.ts:398-410`). Fine today; note for the iOS-version matrix (WKWebView WebRTC needs iOS 14.3+, Expo 54 targets 15.1+).
### P3-5 — `readTransportPolicy` maps anything but `"relay"` to `"all"` (`types.ts:408-410`). Not a confidentiality downgrade (relay is about reachability), but a malformed policy silently loses relay-only intent; log/diagnose when the field is present and unrecognised.

## (B) What is already good

- `ReconnectingSocket` is generation-fenced and correct on the paths it covers: retire during an in-flight `url()` is honoured (`socket.ts:169-171`), `connect()` is idempotent while connecting/open (`:92-100`), backoff is exponential with 0.7–1.3 jitter (`:255-260`), the watchdog is re-armed per frame (`:196-200`), and all of this is pinned by `socket.test.ts`. No duplicate sockets on fast background/foreground flips.
- Resume sweep order (sockets → queries → transports) is explicit and tested (`lifecycle.test.ts`, `network-source.test.ts`); the socket-observed network epoch is a clever fallback given no NetInfo.
- Signalling is fail-closed: `rtc.config` must be `enabled` and (session) `binding_nonce_required` (`session-transport.ts:287-297`); host `rtc.config` must be bound to the exact host/protocol tuple (`host-transport.ts:612-619`); every `rtc.answer` must carry a signed envelope verified against the pinned host key and the active route before it reaches the WebView (`signed-signalling.ts:51-78`); the worker re-checks sender key and session/nonce (`worker-transport.js:172-182, 207-216`); candidates are withheld until the binding is accepted / the signed offer is on the wire (`:96-105`), and remote candidates are buffered until the answer is applied (`:225-228`). Tests pin the host-vs-session binding rules (`worker-signalling.test.ts`).
- Private key never enters the WebView; RN signs (`signed-signalling.ts:34-49`).
- No SDP/candidate/IP logging anywhere in the RN transport or the worker runtime (no `console.*` in `worker-*.js`; vendor xterm only).
- WebView containment: navigation limited to the bootstrap document, new windows and link previews off, `base-uri 'none'`, `default-src 'none'`, `script-src 'unsafe-inline'` only; pinned by `webview-containment.test.tsx`.
- Data channels are ordered+reliable (daemon requirement), `binaryType = "arraybuffer"`, input chunked at 64 KiB on both sides (`ctl-codec.ts` + `worker-runtime.js:673-684`), output batched at 32 KiB / 8 ms with a stale→snapshot recovery when the write queue overflows (`worker-session.js:147-160`).
- The trust preflight names an unapproved device in a few hundred ms instead of a 25 s watchdog, keeps the error code through the surface (`TerminalSurface.tsx:203-213`), and the overlay auto-retries when approval lands (`terminal-overlay.tsx:290-301`). The Retry remounts the surface with a generation key — a clean full reset.
- Old peer connections are closed on every retry (`teardown` nulls handlers, closes channels then `pc.close()`, `worker-transport.js:231-251`); `onContentProcessDidTerminate` reloads and reopens.
- TURN credential staleness is a non-issue today: every reconnect re-opens the signalling socket and gets a fresh `rtc.config` (24 h TTL, `server/spawn_server/config.py:145`).

## (C) Open questions

1. Does the daemon (webrtc-rs) accept an ICE restart / re-offer on an existing binding? That decides whether P1-4 should call `restartIce()` or just fail fast. (For the daemon review.)
2. Does the daemon answer a second offer for the same session while the first binding is still alive (P1-2), or reply `collision`? Either way the phone should stop sending it.
3. `expo-network` is in the Expo 54 SDK but not installed (`node_modules/expo-network` absent). Adding it is a native change — is a new build acceptable for this branch, or should the NetInfo work wait for the next build?
4. Is `live` on the Legion screen (P2-7) on by default? If so the N-WebView cost applies to every user with several hosts.
5. Does the loopback probe (`probeLoopback`) trigger the iOS Local Network permission prompt on first terminal open (the app declares `NSLocalNetworkUsageDescription`)? If yes, that prompt lands mid-connect rather than in onboarding.
6. Push-triggered foregrounding: a cold launch from a push goes through the normal mount path (fine); a warm launch goes through `active` → resume sweep → surface reopen, and P1-6/P1-3 apply. Worth a device test of "tap a knock push while the terminal is open".
