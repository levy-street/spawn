## B. Findings

**F1 (P1) — Daemon pin-cap exhaustion wedges new approvals silently.**
`merge_browser_pin` bails at 32 (daemon/src/creds.rs:485-486). On the endorsement-adoption path the error propagates out of `adopt_endorsed_browser_pins` (creds.rs:438 `?`) and is swallowed into a daemon-side `tracing::warn!("could not adopt endorsed browser pins")` (run.rs:1035-1040). The approving device saw success (server-side insert passed the server's own 32 cap), the new device's pin simply never lands on the host, and under signed-RTC enforcement it can never connect — with no user-visible signal anywhere. `spawnd login` at cap fails with the bail text on the CLI (login.rs:441 via commit_login_update), which is at least visible. Recovery today: Settings → revoke stale devices → "Clear history" (prune) → server pushes → daemon auto-prunes to live set; or `spawnd creds` wipe (cli.rs:45). Fix: (a) daemon nacks a failed adoption over the WS so the server can mark the pin undelivered and the UI can say so; (b) capacity (used/32) exposed in the host pins API and shown at approval time; (c) proactive warning at ~28/32 suggesting revocation of stale devices. Never auto-drop a pin the daemon holds — removal stays server-live-set-driven (reduce-only) as today.

**F2 (P1) — Revoke does not reclaim pin capacity; only revoke+prune does.**
Both server cap checks count ALL `HostBrowserPin` rows: routes/device.py:581-596 and routes/trust_bundle.py:445-455 (`select(count).where(host_id==…)`, no liveness filter). Pins of revoked devices are only removed when the roster row is hard-deleted by `/prune` (FK cascade). A user who cycles browsers (private windows, cleared storage, reinstalls) and revokes each old one still marches to 32 dead rows per host, then gets `pin_limit` at claim / 409 "host browser pin capacity is exhausted" at endorsement — and web has no copy for `pin_limit` at all (only mobile schemas/devices.ts:84 knows the string). Fix: count capacity against `live_browser_device_id_set` (pin_liveness.py already computes it and is the stated single authority), or delete the pin rows inside the revoke transaction — safe under the trust rules because the deny-list is the key-level tombstone (`RevokedBrowserKey`), the pin row is not part of the deny mechanism, and `_registration_result`/adoption can never re-admit a denied key.

**F3 (P1) — The 365-day daemon token has no renewal and its death is indistinguishable from a network blip.**
Minted exactly once at pairing (routes/device.py:607). The supervisor loop treats every session error identically: class-only `tracing::warn!("daemon control websocket session ended with error")` + exponential backoff, forever (run.rs:580-590; ws.rs connect surfaces only "ws handshake" context). After day 365 the host goes permanently offline while the daemon retries silently; nothing tells the operator to re-run `spawnd login`. Fix: distinguish the auth-rejected handshake (HTTP 401/4401 close) from transport failure, log an actionable "daemon token expired — run `spawnd login`" at error level (rate-limited like the protocol-required path at run.rs:560-578), and add rotation: on authenticated connect with < 30 d remaining, server issues a fresh token in the register ack and the daemon persists it through the existing credential-commit path. Renewal-over-an-authenticated-connection weakens nothing.

**F4 (P1) — Sessions are one 30-day token with no refresh: monthly hard sign-out for everyone.**
`issue_session_token` = 30-day JWT, kind=access (auth.py:69-88); web rides it as the cookie, mobile stores the same cookie JWT as its Bearer. No refresh endpoint exists. Day 30, mid-anything: web `/api/me` → 401 → user null → login; mobile pre-flight expiry check clears the token and hard signs out (auth-token.ts:70-73, client.ts:45-49). Even daily users re-authenticate every month; combined with F3 this is the recurring "session expiry" complaint. Fix: sliding renewal — any authenticated request past the token's half-life re-issues cookie + mobile token (epoch-checked, so "sign out everywhere"/reset still evicts); optionally make the 15-min access token real (memory-only, refreshed from the session token) or delete it.

**F5 (P2) — No stale-device surfacing or ageing anywhere.**
Nothing flags a device unseen for months (prod already has 2 of 16 live devices unseen > 90 d). `last_seen_at` is honestly maintained (register reconcile + approval ask), so the data exists; no UI ranks/marks it, no prompt suggests revocation, and no policy ever ages one out. A pinned device key stays valid for signed-RTC indefinitely. Fix (respecting "revocation is the only removal"): AccessPanel + mobile panel sort by last-seen and badge "> 60 d"; settings nudge when a stale device also holds pins; any auto-expiry must be a real revoke (deny-list entry), which is a product decision — surface-first is the safe default.

**F6 (P2) — Mobile devices panel lacks last-seen and pin context (frontend parity bug).**
`browser-device-row.tsx` renders label + trusted only; web shows "Seen …" (AccessPanel:522,536,978). Per repo rule, an unexplained one-sided gap is a bug. Fix: add last-seen (and waiting/approval state) to the mobile row.

**F7 (P2) — Logout does not invalidate the token; no "sign out everywhere".**
Logout deletes the cookie / clears SecureStore only (routes/auth.py:128; mobile logOut also unregisters push — good). A copied token stays valid up to 30 d; the only evictions are password reset and the OAuth adoption path. Fix: a Settings "Sign out everywhere" that bumps `session_epoch` (all verify paths already enforce it, including `current_user_optional`), and bump on any future password-change endpoint.

**F8 (P2) — Local trust stores only grow; sign-out and account removal clear nothing.**
Web: identity DB hard-fails at 32 accounts (browser-device-identity.ts:373-377), host-pin DB at 256 records including permanent tombstones (browser-host-pins.ts:7,:520), peer keys at 256; the only cleanup is the nuclear "Forget hosts on this device". Mobile mirrors it (256; `deleteAccount` runs only on identity reset). The :661 hostIds-FIFO design is correct (routing metadata rebinds on next resolve; refusing would turn re-pair churn into lockout) — residual risk is only the record-count caps. Fix: per-account "remove this account from this browser/phone" (identity + pins + peer keys + root knowledge; keep the trust-revision floor and local revocation tombstones — they are the memory that prevents re-admission), plus count active vs tombstone records separately so tombstones cannot starve active capacity.

**F9 (P3) — `DeviceApprovalRequest` rows are never deleted.** Resolved/expired rows are only filtered (trust_bundle.py:895); prod holds 8 already. Advisory data with no trust effect — delete resolved/expired rows older than ~30 d opportunistically on the list/create paths.

**F10 (P3) — `PushDevice` disabled rows are kept forever.** Reinstalls mint new tokens while dead rows accumulate with `disabled_at` set (push.py:130). Routing-only data: purge disabled rows older than ~90 d.

**F11 (P3) — Roster tombstone display double-counts churn history.** "Removed devices (n)" (web :808-838) counts roster tombstones, while the real deny-list (`revoked_browser_keys`, 18 rows in prod) is invisible; after "Clear history" the count drops to 0 though the denial persists. Cosmetic, but worth a line of copy ("removal is permanent; this clears the list only").

Existing mitigations worth keeping intact: register re-check against `RevokedBrowserKey` blocks re-registration of pruned keys (browser_devices.py:101-113); pin liveness fails closed on dangling endorsers (pin_liveness.py:34-36); daemon adoption requires a verifiable endorsement chain and prune is reduce-only; revoke pushes recomputed pins to every host immediately (browser_devices.py:400-423).

Verdict: no table is bloated yet, but the shape is proven — deny-list (18) already outnumbers live devices (16) on an 8-user deployment, approval-request rows only accumulate, and 12 % of live devices are already > 90 d stale. The growth is real, just early.

## D. Recommended "device hygiene" feature spec (~15 lines)

1. **Stale-device surfacing**: both device panels sort live devices by `last_seen_at`, badge anything > 60 d ("Not seen since …"), and show a one-tap Revoke on the row (existing revoke flow + confirm). Mobile gains last-seen parity (F6).
2. **Revoke reclaims capacity**: delete the device's `HostBrowserPin` rows in the revoke transaction (deny-list untouched), and/or compute both server cap checks from `live_browser_device_id_set`. Push-to-daemons already follows revoke.
3. **Capacity headroom**: `GET /api/trust/hosts/{id}/pins` gains `capacity: {used, max}`; clients warn at ≥ 28/32 with "revoke devices you no longer use"; `pin_limit`/409 get real copy in BOTH frontends naming the fix.
4. **Adoption nack**: daemon reports a failed pin adoption on the WS; server flags the pin undelivered; the approval UI stops claiming success (F1).
5. **Daemon token renewal**: rotate the daemon token over an authenticated register ack when < 30 d remain; distinct, rate-limited "token expired — run spawnd login" log otherwise (F3).
6. **Session renewal**: sliding re-issue of the 30-day session past half-life on both frontends; epoch semantics unchanged (F4). Add Settings → "Sign out everywhere" = epoch bump (F7).
7. **Local-store hygiene**: "Remove this account from this device" wipes identity/pins/peer-keys/root-knowledge for that account only, preserving revocation tombstones + revision floor; tombstones excluded from the active-record cap (F8).
8. **Row hygiene**: opportunistic deletion of resolved/expired approval requests (> 30 d) and disabled push rows (> 90 d) (F9, F10).
Invariants preserved throughout: deny-list is add-only and permanent; revocation is never weakened or automated away silently; pruning never re-admits (register + adoption checks stay as they are).
